Goal and ground rules

The goal is a real mainline kernel with Debian on lisa, not a halium-style Android container. The phone also has to keep working as an Android phone, so a few rules held for the whole project:

  • Linux lives on slot B; Android (Lyra) stays on slot A. Only boot_b and vendor_boot_b are ever flashed.
  • No fastboot reboot (resets are Power + Volume-Down for 10 s), no --spl_downgrade, no MIUI, never lock the bootloader.
  • After every flash, check that slot A is still bootable.

Slot-based dual boot is only a test setup. Virtual A/B updates write the inactive slot, so the first Android OTA would wipe Linux. The long-term plan is a boot menu inside the Android boot ramdisk that kexecs into mainline, so it survives every update. Whether kexec works on this SoC is still the open go/no-go question.

How lisa boots phase 0

  • The bootloader (ABL) uses boot header v3. boot.img carries only the kernel; the device tree, the vendor ramdisk and the kernel command line come from vendor_boot of the same slot.
  • That is why fastboot boot with a mainline image just resets the phone: ABL still uses the slot's Android vendor_boot and its DTB. We build our own vendor_boot, as postmarketOS does.
  • ABL picks the DTB by id, so the mainline DTB gets qcom,msm-id = <0x1db 0x10000> and qcom,board-id = <0x1000b 0x00> injected at build time.
  • An erased dtbo_b boots. A valid dtbo with no matching overlay makes ABL refuse the boot.
  • Every failed boot counts against the active slot. After a few, the slot is marked unbootable.

Mainline already had a basic sm7325-xiaomi-lisa.dts (framebuffer, touch, Wi-Fi, Bluetooth, modem, GPU). Panel and sound only existed in an older fork, and the community sc7280-mainline tree was the main SoC reference.

First boot v1–v5

The first image was a tiny busybox initramfs that brings up a USB ethernet gadget and telnet. Over the cable the phone is 172.16.42.1. It booted on the first serious try. Two build fixes were needed: CONFIG_OCMEM=y (the GPU depends on it) and small fixes to compile the fork's panel driver on 7.4. With the Qualcomm firmware in /lib/firmware, the ADSP, CDSP and WPSS remote processors came up.

The display saga v6–v15

The panel chain is MDSS/DPU → DSI0 + 7 nm PHY → a csot,vtdr6130 command-mode panel with DSC. It took ten builds to get a picture.

Black screen

Cause
The fixed regulator on gpio46 that feeds the panel's logic supply was switched off when it registered.
Fix
regulator-boot-on + regulator-always-on on it and on two LDOs.

Frozen splash

Cause
The MDSS reset kills the bootloader's continuous splash.
Outcome
Keeping the splash alive gave black every time. Dead end, abandoned.

"DSI PLL(0) lock failed"

Cause
A bug in the 7 nm DSI PHY driver: the PLL bias enable/disable helpers toggle only PLL_SHUTDOWNB and also need to toggle DIGTOP_PWRDN_B.
Fix
Patch both helpers in dsi_phy_7nm.c. Found through a bug report on another Snapdragon tablet port. Reading registers needed /dev/mem, and on this DSI block every register sits at +4.

Timeouts on every frame

Cause
Our own DCS reads. A read turns data lane 0 around, and this panel never hands it back.
Fix
Never read from the panel: no init-time read, no brightness read-back. A write-only debug file lets us send raw DCS commands.

Black after boot, everything reports OK

Cause
The first panel init at boot doesn't take, probably because the bootloader leaves the panel running.
Workaround
Blank and unblank once after boot. The initramfs does it, and so does a systemd service in Debian. The proper kernel fix is still open.

USB host and the missing PD mapper v16–v18

Debian first ran from a USB drive through a hub, and the hub got no power. The root cause was that qcom_pd_mapper was built as a module and nothing loaded it. It is an auxiliary device without a modalias, so module coldplug never sees it. Without it the ADSP's charger/USB-C service never registers. That means no UCSI, no Type-C class, no host mode, no VBUS, and a battery driver stuck on EAGAIN.

Fix: modprobe qcom_pd_mapper before coldplug. The battery read 99 % at once, and the port switched to host mode as soon as a hub was attached.

One build silently skipped the root-drive search: the patch script's "already applied" guard matched a string that a comment edit one line earlier had just inserted. Since then, guards check for something only the real change adds, and the image is unpacked and checked before every flash.

Finding a home for Debian v19

A rootfs on a USB drive is fine for bring-up, but not for a phone. The internal options:

  • super has about 2.1 GB free, too small, and Android's virtual A/B updates write the next slot into exactly that space.
  • userdata is 113 GB but uses metadata encryption with a key in the TEE. Linux cannot read it, so a loop image inside it is impossible.

So we backed up the GPT, shrank userdata to 79 GB, and added a 32 GiB lyra_root partition. That wiped Android's data, which Android simply re-creates on next boot. The v19 initramfs prefers a USB drive labelled lyra-root (the rescue disk) and otherwise boots the internal partition.

Slot B kept falling back

After about seven Linux boots the phone booted Android again: slot B was marked unbootable. Nothing under Linux told the bootloader the boot had succeeded, so its retry counter ran down. Debian's qbootctl marks the slot good on every boot. It needed a small drop-in to wait for udev's partition links.

Phosh

phosh-core installed and ran, with a lock screen, Wi-Fi in the UI, an app grid and the squeekboard on-screen keyboard. Three things needed fixing:

  • phosh.service conflicts with getty@tty1, and the enabled getty won at boot.
  • phosh-core also pulls in greetd, which sometimes won the race to start the session. We disabled it to go straight to the lock screen.
  • With no charger visible, the phone auto-suspended and dropped SSH. Sleep targets are masked until charging works.

There's no auto-rotation: lisa's accelerometer sits behind the ADSP sensor hub, which mainline does not support.

The battery storm v18–v21

With the battery driver bound, systemd-journald kept getting killed after 90 s. The console was full of time_to_full_avg ... -110 timeouts, about one a second.

Driver bug: a missed completion

Cause
The firmware does answer that request, with an unexpected payload length. qcom_battmgr flags the error and returns without completing the request, so every query sits out a 1 s timeout. One battery notification a second, each followed by a full property read, makes a uevent storm that stalls udev and journald.
Fix
Complete the request on every bad-length path and rate-limit the warnings. A full property read went from over 20 s to 7 ms.

Xiaomi's property map is shifted

Symptom
Temperature 540 °C, cycle count in the hundreds of millions, model name as a number.
Cause
Xiaomi's firmware inserts an extra battery property at index 12. Found by reading Xiaomi's published lisa kernel source.
Fix
A per-device index offset. Now: 28 °C, Li-poly, 348 cycles, the right model string.

Both fixes are being prepared for upstream.

Bluetooth, Wi-Fi and MAC addresses

  • The bootloader passes no Bluetooth address or Wi-Fi MAC. Bluetooth came up unconfigured, and Wi-Fi picked a random MAC (and a new DHCP lease) every boot. A small boot service now derives stable, locally administered addresses from the device serial.
  • btmgmt never exits without a TTY. It works, then hangs. Wrapping it in script fixes that.
  • Wi-Fi dropped every few minutes. The firmware boots with the world regulatory domain, where 5 GHz DFS channels are passive-only. Roaming to the 5 GHz access point timed out, and NetworkManager eventually gave up. Setting the country (iw reg set) at boot fixed it.

Speakers v22

The ADSP speaks APR (the "Elite" audio firmware), so the mainline q6afe/q6asm/q6routing stack applies. Lisa has two NXP TFA9873 amplifiers on I²C fed by primary MI2S, the same as the Xiaomi taoyao in sc7280-mainline, whose TFA9872/9873 driver we picked up.

  • Left is the top speaker and right is the bottom one, checked by ear.
  • PipeWire needed a UCM profile for lisa before it would offer a normal "Speakers" sink.
  • Silent playback while everything said RUNNING: PipeWire picked 24-bit samples, and the speakers only play 16-bit. A WirePlumber rule pins S16LE for now.

Microphones v23–v26, in progress

The mics sit on a WCD9385 codec, connected over SoundWire, behind the LPASS RX/TX/VA "macros". On this firmware the macro clocks are owned by the DSP, so they vote through q6afecc.

  • v23: the codec enumerated on both SoundWire buses and every DAPM widget on the capture path powered up, but every sample was exactly zero.
  • v24: extra front ends, so playing and recording at the same time works.
  • v25 tried the older TX macro input layout. That was the wrong direction.
  • The breakthrough was a sweep of every ADC, input mux and SoundWire input. Lisa's main microphone (AMIC5 → ADC4) carries real audio on SWR_MIC5, and a quiet test tone shows up exactly where it played. That confirms the newer (v9.2) TX macro layout is right for SM7325.
  • Still open: everything on the codec's first SoundWire data port (ADC1/ADC2, the second mic) reads exact zeros, whatever ADC or input feeds it. Retiming that port (v26) changed nothing on the wire, so the cause lies elsewhere.
Don't trust "it's all powered up". The decisive data came from sweeping every combination and looking for any non-zero sample, then checking with a quiet test tone.

What's next

  1. Make the main mic the default in PipeWire, and find the second mic's zero data.
  2. Earpiece (switched by a GPIO between the top amplifier and the earpiece).
  3. Fix the panel's first init in the kernel (the garbled white screen on some boots).
  4. Charger detection, then modem stability and calls.
  5. The kexec boot menu, so Linux survives Android updates.
  6. Upstream: the battery fixes, the DSI PHY fix and the lisa device tree.

Lessons

  • Read the boot chain before flashing anything. Header v3 and vendor_boot explained why the obvious fastboot boot could never work.
  • Silent zeros and "RUNNING" mean nothing. Both the speaker and the mic bugs looked healthy at every layer we asked.
  • Vendor source is the ground truth for quirks. Xiaomi's kernel and Android audio configs settled the battery property shift and the mic wiring.
  • Keep a way back. Slot A untouched, a USB rescue disk, a GPT backup before repartitioning, and every image checksummed before and after flashing.
